# Граница Jev, кода и состояния — Validation 2A.1

`Docs/jev_context.md` задаёт Jev роль атомарного семантического датчика. Ниже описан замороженный контракт этого запуска и его фактическая воспроизводимость; интеграции не было.

| Classifier | JEV / semantic | CODE / state | STATE между событиями |
|---|---|---|---|
| R01a | Найти явно названную роль клиента для текущего gate. | Не выводить роль из должности контакта. | Ключ актуального gate и исходное свидетельство. |
| R01b | Определить конкретное ожидаемое действие по тому же gate. | Не склеивать фразы разных gate. | Тот же ключ gate, роль и действие. |
| R01c | Найти ограниченную дату, событие или результат этого действия. | Сравнение/истечение даты выполняет код при необходимости. | Тот же gate и контрольная точка. |
| R03 | Назвать активную техническую задачу и оценить, хватает ли полученных данных для её текущей проверки. | Не подменять достаточность числом файлов или полей. | Версия активной задачи, необходимые и полученные клиентские данные. |
| R04 | Найти клиентское конкретное проверяемое требование, ограничение или вопрос. | Накопить `ever YES` по времени, сохранив доказательство. | Флаг и первое подходящее событие. |

## R01: один gate, три датчика, один уровень

Jev должен отвечать отдельно на три вопроса, используя одну и ту же текущую внутреннюю развилку решения клиента. Код получает `R01a/b/c` и `gate_key`: `2` только при трёх `YES` по одному gate; `1` при частичной подтверждённой структуре; `0` при трёх `NO` после содержательного разговора; иначе `UNKNOWN`. Код не может «добрать» роль из одного согласования, действие из другого и срок из третьего. Для следующего запуска потребуется лучше определить, какое обсуждение достаточно для `NO`: именно эта граница дала семь общих споров `UNKNOWN` на контрольной выборке. Текущий R01 не готов для Jev или holdout.

## R02: извлечение события и детерминированный жизненный цикл

Семантический слой на каждом новом сообщении выделяет конкретное **клиентское** обязательство: владельца, обещанное действие, срок либо ожидаемый результат, последующее сообщение о выполнении, переносе, конкретной замене и явном срыве. Продавцова задача и отсутствие ответа не являются клиентским обязательством или срывом.

Код хранит `commitment_id`, `agreed_at`, `owner`, `action`, `due_at`, `expected_result`, `replaces_id`, `completion_evidence_at`, `reschedule_evidence_at`, `explicit_missed_at` и ссылки на события. По состоянию на cutoff он выбирает действующее обязательство, сравнивает срок, следует по ссылке замены и считает **только явно подтверждённые** пропуски. `REPEATEDLY_MISSED` требует минимум двух таких пропусков без нормальной конкретной замены. Если срок прошёл, но ни выполнение, ни срыв не подтверждены, код возвращает `UNKNOWN`.

Кодовая часть проверена как детерминированная, но её вход ненадёжен: весь производный R02 совпал лишь в 14/30 срезов. Поэтому разделение semantic/code пока не делает этот признак готовым к Jev или holdout.

## Остальные границы

R03 остаётся семантически шире атомарного вопроса: выбор текущей задачи и оценка «критически недостающих данных» дали 8/30 содержательных разногласий. Его нельзя заменить подсчётом фото/файлов. R04 численно устойчив как семантическая проверка `YES` против недостатка сведений, а код должен только сохранять накопленный факт. Но `NO` отсутствовал в контрольной выборке; перед заморозкой для holdout нужна отдельная проверка этой ветки, без изменения текущего контракта задним числом.
