# Temporal sanity — Validation 2A.1

Проверка использует фактические timestamp cutoff; у 8 из 23 сделок порядок процентных и фиксированных срезов отличается от записи `D3→D7→T25→T50→T80`. Производные состояния рассчитаны одинаковым кодом из извлечённых событий на каждом срезе.

| Проверка | Результат | Толкование |
|---|---|---|
| R04 `CUMULATIVE_FACT`: `YES` не должен исчезать | 0 нарушений на 23 траекториях | Режим накопленного факта соблюдён в основной разметке. |
| R01a/b/c при том же `gate_key`: `YES→NO` | 1 переход: 18731, T50→T80, R01c | Возможно, старая контрольная точка истекла или gate был переименован без смены ключа; требует точного определения актуального gate. |
| R03 при том же `active_task`: `SUFFICIENT→PARTIAL/INSUFFICIENT` | 0 переходов | Падения были бы допустимы при новой задаче, но для одной и той же задачи не наблюдались. |

Производный R01 на 115 срезах: `2` — 29, `1` — 16, `0` — 6, `UNKNOWN` — 64. Большое число `UNKNOWN` следует из строгого требования одного текущего gate и не должно превращаться в нулевой уровень.

Производный R02: `COMPLETED` — 28, `RESCHEDULED_WITH_CONCRETE_REPLACEMENT` — 12, `NOT_DUE` — 9, `MISSED` — 6, `NO_COMMITMENT` — 7, `UNKNOWN` — 53, `REPEATEDLY_MISSED` — 0. Во всех шести `MISSED` код требовал явного подтверждения пропущенного шага; истечение срока без записи о выполнении оставалось `UNKNOWN`. Ноль `REPEATEDLY_MISSED` означает, что этот редкий класс на данном наборе не проверен.

Временные траектории и конкретные переходы записаны в [temporal_checks.json](./temporal_checks.json). Срезы унаследованы из Validation 2A: события смены стадии, одно окончательное решение клиента и два агрегированных worklog с будущими обновлениями исключены только из производных файлов. Датасет не менялся.
